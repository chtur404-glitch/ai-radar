# 文章寫作規格（content/articles/*.md）

這份文件是 AI Radar 文章的唯一格式與語氣規範。寫文章前先讀完它，並參考
`content/config.yml` 的分類 id。

## 1. 這個網站要什麼

AI Radar 是繁體中文（台灣用語）的 AI 工具與技術介紹網站。每一篇只講一個工具／模型／技術／應用。

**唯一最重要的目標：讓讀者產生興趣。** 讀完應該覺得「這東西真有意思，我想去玩玩看」。
明確不是：完整教學、工具資料庫條目、評測排行榜、新聞快訊。
判斷標準：如果寫完像產品說明書或維基條目，就是寫壞了。

## 2. 檔案位置與命名

- 一篇文章一個檔案：`content/articles/<slug>.md`
- slug：全小寫、`-` 分隔、只用英數字（例：`zonos3-mini.md`、`nano-banana-pro.md`），不含日期。
- 除了指定的 `.md` 檔，不要建立或修改任何其他檔案。

## 3. Frontmatter（檔開頭，`---` 包住）

格式是 mini-YAML，只支援：純量、`[a, b]` 內聯陣列、`- ` 開頭的區塊陣列、
以及兩層縮排的 map。字串一律加雙引號，縮排固定 2 空格。

```yaml
---
title: "標題（20–34 字，有具體物件＋好奇心缺口，不要標題殺）"
slug: nano-banana-pro
summary: "40–70 字，說明這是什麼 ＋ 為什麼有趣"
category: image
tags: [圖像生成, 文字渲染, 資訊圖表]
date: 2026-11-16
featured: true
rank: 1
cover:
  motif: image
  palette: amber
tool:
  name: "Nano Banana Pro"
  maker: "Google DeepMind"
  url: "https://blog.google/innovation-and-ai/products/nano-banana-pro/"
  type: "圖像生成與編輯模型"
  open_source: false
  cost: "Google AI 方案或 API 計費"
sources:
  - label: "Google 官方部落格（2025-11-20）"
    url: "https://blog.google/innovation-and-ai/products/nano-banana-pro/"
highlights:
  - "3–4 條，每條 15–35 字，放具體數字或反直覺的事實"
extend:
  - "3 條延伸潛力，每條 20–40 字"
---
```

欄位規則：

| 欄位 | 必填 | 說明 |
| --- | --- | --- |
| `title` | ✔ | 20–34 字。有具體物件、能引起好奇，但不耍曖昧（不要「你絕對想不到」） |
| `slug` | 可省 | 省略時用檔名 |
| `summary` | ✔ | 40–70 字，一句話說清楚它是什麼＋為何有趣。會顯示在卡片與文章開頭 |
| `category` | ✔ | 只能是 config.yml 既有分類 id（見下） |
| `tags` | ✔ | 2–4 個，中文為主，不放泛用詞（「AI」「工具」這種不要） |
| `date` | ✔ | `YYYY-MM-DD` |
| `featured` / `rank` | 可省 | 首頁精選；`rank: 1` 是最大卡，只在少數文章上使用 |
| `cover.motif` | ✔ | `image` / `video` / `audio` / `agent` / `coding` / `fun`，決定封面圖形狀 |
| `cover.palette` | ✔ | `amber` / `violet` / `cyan` / `indigo` / `lime` / `magenta` |
| `tool.*` | ✔ | 工具資訊卡內容。`open_source` 只填 `true` / `false` / `unknown` |
| `sources` | ✔ | 至少 3 條，其中至少 1 條是一手來源（官方部落格／論文／官方文件／GitHub repo） |
| `highlights` | ✔ | 3–4 條，讀者只看這裡也能抓到重點 |
| `extend` | ✔ | 3 條延伸潛力（這技術還能拿去做什麼，可以合理外推但要標明是推測） |

分類 id：`agent`（AI Agent）、`coding`（程式開發）、`image`（圖像與設計）、
`video`（影片生成）、`audio`（語音與音樂）、`fun`（趣味應用與研究）。

## 4. 正文

- 長度 **450–650 字**（不含 frontmatter，中文字計）。
- 繁體中文（台灣用語），工具與模型名稱保留英文原文。不要用 emoji。
- 建議結構（可依題材調整，不必每篇都有）：

  ```
  ## 一句話說它是什麼
  ## 它到底能做什麼
  ## 為什麼值得注意
  ## 實際可以怎麼用
  ## 還沒被驗證的地方
  ```

- 開頭第一段直接給最有趣的事實，不要鋪陳、不要「近年來 AI 快速發展」這種開場。
- 可用 `##` 小標、清單、粗體、引用區塊 `>`、小表格、行內程式碼。
- 不要在正文重複 frontmatter 已有的標題或摘要。
- 篇幅不必求全：寧可只講兩件有趣的事，也不要為了塞滿欄位而稀釋重點。
- 不要用「首先／其次／最後」這種作文腔；不要用行銷誇飾（「革命性」「顛覆」）。

## 5. 事實紀律（最重要的規則）

1. 每個數字、日期、名稱、功能都必須來自你**實際查證過的來源**，並對應 `sources` 中的一條。
2. 標明數字是誰說的：官方自稱、論文自報、第三方評測，三者不可混用。
   沒有第三方複現的數字要寫明「官方自稱，尚無獨立驗證」。
3. `sources` 的 URL 必須是你真的查到、且看起來存在的一手/可信來源。
4. 查不到的事就不要寫。**絕對不可編造數字、日期、功能、價格或連結。**
5. 保留原始出處與體驗入口（`tool.url`），讓讀者能自己去看。
6. 若一則資訊只有二手（新聞轉述）來源，就標明「據 X 轉述」並降低語氣強度。

## 6. 語氣範例

壞（產品說明書 + 空話）：

> 近年來人工智慧快速發展，本文將介紹一個新的文字轉語音模型。
> 該模型具有高效能與高品質的特性，並且支援多種語言，值得使用者關注。

好（直接、具體、有畫面）：

> 一句話複製你的聲音，然後在你的手機瀏覽器裡即時講出來——不用裝任何東西。
> 這個模型只有 8.86 億參數，Zyphra 官方自稱在 Pixel 9 上第一段音訊不到 570 毫秒就出來。

## 7. 送出前自我檢查

- [ ] frontmatter 每個必填欄位都在，且格式符合第 3 節
- [ ] 正文介於 450–650 字
- [ ] 每一個數字都能對應到 sources 的某一條
- [ ] 至少一條一手來源
- [ ] `tool.url` 和 `sources` 的連結都是實際查到的
- [ ] 讀完會想去看那個工具（不是「喔，知道了」）
